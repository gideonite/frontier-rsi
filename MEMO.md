# Research memo: why FrontierRSI agents' own validation misled them, and what the data can and cannot say

*Scope: follow-up to `FINDINGS.md`. No new benchmark runs, no paid APIs. Evidence cited as `trial#step` (read with `analysis/trace/brief.py`); **[obs]** = observed in a trace or file, **[inf]** = inference, **[spec]** = speculation.*

## 0. Corrections to the first pass (important)
1. **The ambiguity count was wrong.** `raw_score` is joined to trials by (model, task, reward). When both trials of a cell tie on reward but have different raw values, *either* assignment is possible, so **both** trials are ambiguous. The first build flagged only one of the two. Correct figure: **134 ambiguous cells = 268 of 486 trials (162 claude-code: 78)**. `scripts/build_dataset.py` is fixed; `data/trials.jsonl` and all outputs were regenerated.
2. **It cannot be resolved deterministically [obs].** Oddish rows carry no raw score; the leaderboard's trial order matches trial-id order in 96/104 cells where the pairing is known (92.3%, Wilson 95% CI 85.6-96.1%), so id-order is a decent heuristic but not a rule. Reward is zero-inflated (322/486 exactly 0), so ties are common and concentrated in poor outcomes.
3. **"Drop ambiguous trials" is itself biased.** Cells with different rewards are cells where at least one trial scored >0, so the remaining 84 trials are the *better* runs (median q 0.94-0.96 for all three models; the Kimi-vs-Claude gap disappears). Because a within-cell swap leaves the cell mean unchanged, I added a **swap-invariant cell-level analysis** (`analysis/cell_level.py`) that uses all data, plus a heuristic-resolved sensitivity run (`analysis/ambiguity.py`).
4. Consequence for finding 1 of `FINDINGS.md`: the *between-model* association survives (cell level, within task: runs/hour rho -0.38 [-0.60,-0.12]; first official run later +0.33 [+0.08,+0.57]; n=77 cells), but it is a comparison between Kimi and the Claude models. The *within-model* test is **null but under-powered** (42 unambiguous cells; runs/hour -0.12 [-0.43,+0.17]), so I can no longer say effort "does not predict" quality, only that no within-model effect is detectable and a moderate one is not excluded.

## 1. Why did two agents' validation scores diverge from official scores? (`pt-multifile-rl`)
| trial | official | own measure | own eval set | final run | 
|---|---|---|---|---|
| Fable `-123` | **0.087** | 0.750 (`#408`,`#423`) | 112 = 40 real samples + 72 self-generated | LR 2e-5, 35 steps, 7071 s, 640 generated rows (`#412`) |
| Fable `-127` | 0.770 | 0.815 (`#318`) ; 0.75 on the 40 real samples alone | 480 = 40 real + 440 generated | LR 3e-5, 26 steps (~81 min), 448 rows |
| Opus `-115` | **0.147** | 0.829 (`#261`) | 280 generated; the 40 real samples were *in the training pool*, so no real-sample check | LR 3e-5, 46 steps (`#251`), 1760 rows |
| Opus `-126` | 0.817 | 0.863 | 240 = 40 real + 200 generated (**the 40 real samples were also in its pool**, so, like `-115`, no clean real-sample check) | LR 3e-5, 128 eps/step, 50 steps, 9990 rows |
Untrained model: 0.543 officially. Both failures are *below* it.

**Observed facts that constrain explanations**
- **Same distribution, base transfers [obs].** The hidden set (`tests/held.jsonl`) has 75 projects per level, 96% of its function slots use function names present in the 40 samples (78 vs 73 distinct names), and the base model scores 0.543 on it vs 0.525 (21/40) on the samples (`-123#408`). A distribution-shift story would need the *trained* model, not the base, to transfer badly.
- **The validated model was good on real samples [obs].** `-123#408-409`: official `score.py` on the 40 real samples, base 21/40, trained S1 29/40 (0.725, won 9 / lost 1). Yet the graded trained model solved 0.087 of 300 (about 26), roughly 25 sd below what 0.725 predicts (z ~ -25). This is not sampling noise or a known-trap effect.
- **The suspected "trap" function is equally common [obs].** `meeting_rooms` appears in 34/300 hidden projects (11.3%) vs 5/40 samples (12.5%). Even a 0% solve rate on those would cap `-123` near 0.67, not 0.09.
- **Submission = validated pool [obs].** md5 of `/app/rl_pool/pool.jsonl` equals the S1 pool that was trained and scored (`-123#173,#315,#393`); same for `-115` (poolC, `#257`).
- **No trainer difference [obs].** `tests/train_rl.py` is identical to the agents' `train_rl.py`, and `tests/kit` is identical to `posttrain-kit` (only the README/VENDORED files differ). The agents did patch their copy (`-123#84`, `-127#182`: adding checkpoint options), but `-127` did this and succeeded, while `-115` and `-126` patched nothing (`analysis/pt_modified_trainer.py`).
- **The graded run is a fresh training run [obs]** (`tests/grade.py`): the grader retrains from `/opt/base` and evaluates that model; the agent's measured model is a different training run with the same files.
- **Training in this setup is fragile, per the agents themselves [obs]:** LR 1e-4 "collapsed the model to 0.0" (`-127` final message); entropy ~0.002-0.005 from step 36, "policy collapse" (`-115` final message); signal loss at 64 episodes/step (`-126`); same pool/config trained twice gave one clear improvement and one flat run (`-119`, numpy variant). All four hand-ins were validated by **one** full run (a full run + scoring costs ~2.4 h of an 8 h budget).

**Inference [inf].** The most economical explanation consistent with every fact above is that the grader's training run did **not** reproduce the validated model, i.e. run-to-run training variance (possibly a collapse) and not a validation-design flaw. The two successes and two failures all used generated eval sets of similar construction, so *validation-set design does not separate them in this sample*. **I therefore retract the first memo's framing of "validation representativeness" as the explanation for this case**; what the traces support is "n=1 training run per candidate".
**Speculation [spec].** A late-run entropy collapse (`-115`) or a wall-clock edge effect (`-123`'s run ended at 116.8 of 120 min) could make the graded run diverge; neither is testable from the traces.
**Base rate.** Across all five post-training tasks, **6 of 90 trials are definitely below the untrained baseline, 26 are undetermined (ties), 56 above** (swap-safe classification), so catastrophic hand-ins are a task-level phenomenon, not a Fable/Opus quirk (Kimi: 0 below, 2 invalid).
**Decisive test (needs GPU, not run):** retrain the `-123` pool/config three times with the unmodified trainer and score on the 300 hidden projects; the variance of the result is the missing quantity.

### 1b. Pairwise trace comparison (same model, same prompt)
No process feature cleanly separates the failed from the successful run in either pair; each candidate difference has a counter-example:
- *Training to the wall-clock cap* (`-123`: 35 steps/118 min; `-115`: 46 steps/117 min) vs `-127` stopping at 26 steps/~81 min. But `-126` (success) also ran 50 steps/116 min, and Kimi `-130` ran 57 steps at the same 64 episodes/step and LR 2e-5 as `-123` and scored 0.78.
- *64 vs 128 episodes/step* (`-126` switched to 128 after diagnosing that small updates vanish in the bf16 rollout copy). But `-127` and Kimi `-130` used 64 and succeeded.
- *Sequencing rows by inverting the trainer's seeded shuffle* (`-123`, `tools/make_seq.py`, `#145`): the kit's shuffle is `random.Random(seed=0)` and the grader's kit is identical, so the order should reproduce [inf]; it is only a risk if the grader dropped rows the agent's check kept.
What the failed runs share with the successes: one validating run, late hand-in (`-115` installed its final pool 2 min before the end, `#257`), comparable LRs (2e-5 to 3e-5). What stands out: **both failing agents had seen collapse in-session and treated it as a hyper-parameter problem, not a variance problem.** `-123`'s run A (LR 1e-4) went from reward 0.72 to 0.0 with every group all-wrong by steps 9-10 (`#152-157`); it lowered the LR to 2e-5 and validated once. `-115` reported entropy 0.002-0.005 from step 36 of its final run and wrote "if the graded run collapses earlier than mine did, it will gain less", then handed in. (`-127` also saw a collapse at 1e-4.) Across all 18 trials on this task, the other 14 scored 0.60-0.83 with no collapse; the 2 collapses are both Claude runs (`analysis/pt_timeline.py`, `pt_curves.py`).

### 1c. Reproducing the trainer's seeded row order: not Anthropic-specific
The trainer shuffles each label's rows once with `random.Random(0)` and walks through them, so the rows used at each step are a deterministic function of the pool file. Keyword scan of all 90 post-training traces (`analysis/seed_order_scan.py` plus a text search), each hit read by hand; true positives:
| trial | use | official |
|---|---|---|
| Fable `pt-multifile-rl-...-123` | **control**: invert the shuffle so file order = order of use (`#145`, `#211` asserts it) | 0.087 |
| GPT-6 Astra `pt-chained-...-130` | **control**: "Invert that shuffle so all four tasks in a step appear in the original group order" (`#397`) | 0.287 |
| GPT-6 Astra `pt-multifile-scipy-...-117` | **control**: invert the shuffle for focused arms (`#409`) | 0.373 |
| Fable `pt-multifile-scipy-...-123` | **analysis**: replay the shuffle to map each logged group to its pool row (`#259`) | 0.677 |
| GPT-6 Astra `pt-chained-...-133` | **analysis**: "independently replay the trainer's label insertion and shuffle loop" (`#491`) | 0.233 |
| Opus `pt-chained-...-126` | **analysis**: "replaying the trainer's seeded task order against its training logs" (final report) | 0.133 |
| Kimi `pt-multifile-rl-...-129` | awareness only: "trainer fixed seed0 ... repeats same selected rows", used to hold row selection fixed across comparisons (`#139`) | 0.800 |
Other hits were false positives (agents' own `random.Random(0).shuffle` in data generators; domain code named "replay"). So 3 models (Fable, Opus, GPT-6 Astra) reproduced the order in 6 of 90 trials; outcomes span 0.09-0.68, so it does not track success. [inf] The order is the one thing that *does* reproduce between the agent's run and the grader's; the sampled rollouts do not, which is why fixing the order does not make a run repeatable.

### 1d. Where run-to-run variation comes from, despite `--seed 0`
[obs, code] Everything in the trainer is seeded: the per-label row shuffle (`grpo.py` l.437-446), the label draw per step (`train_rl.py` `next_batch`: `state.rng.choices`), and every rollout request (`rollouts/multiturn.py` l.56-60, a seed drawn from the same `state.rng`). No deterministic-kernel mode is enabled. [inf] Divergence therefore starts from non-bit-exact GPU arithmetic (batched vLLM inference and training kernels) or sandbox timeouts, and is amplified because (a) one different token changes an episode, its reward, the gradient and all later rollouts, and (b) the number of seeds drawn depends on episode lengths, so the shared `state.rng` stream shifts and, for multi-label pools, even the projects drawn change.
[obs, direct] Fable `pt-multifile-numpy-...-119` trained the **identical pool and config twice** on the same machine: 0.586 vs 0.436 on the same 140 projects (base 0.436), and reports "the two 12-step runs see different projects from about step 3" and learned different habits. This is the in-trace demonstration that a fixed seed does not make a run repeatable here; it does not by itself prove that the graded runs of `-123`/`-115` collapsed.

## 2. GPU timing: do agents and the grader measure comparable quantities?
- **By construction yes [obs].** For `kernel-causal-attention` the grader's `test_sweep_worker.py` and the dev `sweep_worker.py` differ only in import names and docstrings; both use protocol `resident-whole-sweep-cuda-graph-v3`, the same 100 public-generator workloads, and one timed replay per seed. The grader takes the median of 5 fixed seeds; agents time seed 101 (`develop.py --count 100`; verified on all six traces, e.g. `-79#96`). Seed choice changes dev times by <=5% in most traces (46.4 vs 46.1 ms; 42.0/42.0/41.9), at most ~30% (logit 0.69 vs 0.91), so seeds do not explain a 2.5-24x gap.
- **Yet the numbers differ by a task-specific constant, not a factor [obs; non-ambiguous trials only, n=4-6 per task].** official minus dev: causal +62.5 ms (CV 1%), masked +34.9 (3%), single-query +7.5 (1%), rectangular +3.1 (2%), parameter-update +2.8 (6%); in all five, the offset varies *less* than the ratio does (`analysis/kernel_offset.py`, `figures/selfreport_vs_official_kernels.png`).
- **Consequence [obs]:** official scores compress real differences. In `kernel-parameter-update`, dev times span 0.16-0.58 ms (3.6x) while official scores span 2.93-3.27 ms (11%), which is why that task's q is 0.90-1.0 for everyone. A 3.6x-faster kernel is nearly indistinguishable on the official metric.
- **Two exceptions [obs, all-trial data so pairing uncertain]:** `kernel-logit-selection`, where official minus dev ranges 2.6 to 12.2 ms across candidates (all six report 0.68-0.91 ms, official 2.6-13.0), i.e. a candidate-specific penalty the dev run did not reveal; and `fragmented-state-attention`, where official is *faster* than dev by a constant ~0.45 ms.
- **Cause: unresolved [spec].** Same code path implies the difference lies in run conditions or an unlisted grader step (cold clocks/power state for a single scored replay, sandbox user, isolation). The repo cannot distinguish these without a GPU. Practical implication: treat the dev tool as a *rank-preserving but compressed* proxy (within-task Spearman between dev and official q: -0.38 [-0.74,-0.11] on non-ambiguous kernels, n=30).

## 3. What is actually interesting
1. **Self-validation did not fail in the way I first suggested; the grader's retraining is the unobserved variable.** The data are consistent with "one training run per candidate, ~2 of 4 catastrophic", which is a statement about agent protocol (no replicates under a 2.4 h/run cost) and about training fragility, and is checkable with 3 reruns.
2. **A benchmark-measurement finding, not an agent finding:** several GPU tasks' official metric contains a candidate-independent offset that compresses 3-4x kernel differences into ~10% score differences; reward saturates for strong agents regardless of effort.
3. **A methods finding:** joining scores to trajectories by reward silently loses trial identity for 55% of trials, and the obvious fix (dropping them) conditions on the outcome. Any future dataset release should carry the trial id with the raw score.

## 4. Limitations
n=2 per cell; model confounded with harness; the pt-multifile conclusions rest on 4 traces and one unobserved retraining; GPU conclusions use the 30-53 trials with parseable self-reports and regex extraction (verified by hand only for logit-selection); no kernel was re-timed; all causal statements above are labelled [inf]/[spec] and none were tested interventionally.
